- `offscreen.html` must load `vendor/tfjs/regenerator-shim.js` immediately before `vendor/tfjs/tf.min.js`, or the pinned TF.js bundle's transitive pre-`globalThis`-guard regenerator-runtime throws the MV3 CSP `EvalError` at script-load time (before any model or backend code runs) instead of the shim's predeclared `regeneratorRuntime` letting its own fallback assignment succeed; see `vendor/tfjs/README.md`. MoveNet and BlazePose load their graph models directly from TF Hub (`MODEL.modelUrl` is an `https://tfhub.dev/...` URL, `fromTFHub: true`) rather than a locally vendored artifact - MoveNet's license isn't cleared for redistribution, and this avoids bundling BlazePose's multi-megabyte weights too. `tfhub.dev` 302-redirects those URLs (and every weight-shard request under them) through `kaggle.com` to a signed, time-limited `storage.googleapis.com` URL; a bare `HEAD` request 404s there (misread once as the host being dead) but `GET` works, which is what `fetch`/`tf.loadGraphModel` actually send. `pose-model-selector.js`'s availability probe skips its normal fetch-reachability test for any `https://` `modelUrl` and reports available without confirming the model actually loads (BlazePose is excluded: its probe refuses it as work-in-progress before any URL check).
- `blazepose-adapter.js`'s graph model (`ld_3d`, `output_poseflag`, plus three other outputs) must be executed with `model.execute(input, [MODEL.landmarkOutputName, MODEL.presenceOutputName])`, not a bare `model.execute(input)`: TF.js returns a bare call's outputs in the graph's own declared order (poseflag, heatmap, world_3d, ld_3d, segmentation for this model), not `[landmarks, presence]`, so an unnamed call silently decodes the wrong tensors as landmarks. Verified against the real hosted model, not a mock.
- Dedicated headed Chrome validation must load `dist/` through the native `chrome://extensions` picker: Chrome-branded 152 ignores the command-line unpacked-extension flags in the remote-debugging setup. See `docs/e2e-smoke.md` §1; never attach the logged-in browser. The raw CDP `Extensions.loadUnpacked`/`uninstall` domain (WebSocket to the browser debugger target, e.g. `ws://127.0.0.1:9333/devtools/browser/<id>`) DOES load and remove unpacked extensions on stable Chrome 152 - no native folder-picker click needed - and the chrome://extensions deep-shadow walk verifies the card. MV3 offscreen documents stay CDP-invisible, but the extension's service worker is an ordinary attachable target: `chrome.runtime.onMessage` listeners installed there tap the offscreen's analyzer-result envelopes, and chrome://extensions errors records the offscreen's console errors (that is how the LiteRT cross-device WebGPU warnings were captured).
